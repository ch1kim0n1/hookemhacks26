# Observability

## Structured logging

`LOG_FORMAT=json` switches the root logger to one-JSON-object-per-line output
that includes `request_id`, `path`, `status`, `latency_ms`, and any extra
fields passed via `logging`'s `extra=` dict. Leave it unset (or set to
`plain`) for local dev.

Every HTTP response includes an `X-Request-ID` header generated by
`RequestLogMiddleware`. Clients can inject their own via an incoming
`X-Request-ID` header to correlate across services.

## OpenTelemetry (tracing)

Optional. Install the `observability` extra, then set:

- `OTEL_EXPORTER_OTLP_ENDPOINT` — e.g. `http://localhost:4318/v1/traces` for an
  OTLP HTTP collector (Jaeger, Grafana Tempo, etc.)
- `OTEL_SERVICE_NAME` — defaults to `clawguard`

If `OTEL_EXPORTER_OTLP_ENDPOINT` is unset, tracing export is disabled (no
overhead).

## Prometheus

`GET /metrics` (standard Prometheus scrape format). **Auth-gated** by default:

- Pass `Authorization: Bearer <token>` or `X-Metrics-Token: <token>`.
- Token resolution order: `METRICS_BEARER_TOKEN` → `ADMIN_API_TOKEN`.
- Set `REQUIRE_METRICS_TOKEN=false` to disable auth (local dev only).
- The endpoint has a separate rate limit governed by
  `METRICS_RATE_LIMIT_PER_MIN` (default 60/min/IP) to prevent a scrape loop
  from starving the API.

Counters / histograms cover detections (by verdict × modality), learning
rounds, defense publishes (success/failure), RPC latency (by method — kept
small to avoid label cardinality blowup), and threat-cache hits/misses/size.

## Alerting (Slack)

Set `SLACK_WEBHOOK_URL` to a Slack incoming webhook. Critical paths (e.g.
learning round failure, RPC timeouts / errors in the async JSON-RPC client)
call the dispatcher when configured.

### Dedupe + severity policy

To prevent alert storms we apply a 5-minute TTL dedupe keyed by
`title|severity`. Identical alerts fired inside the same window are dropped.

Severity policy for RPC errors (`blockchain/async_client.py`):

- `CRITICAL` — only for hard failures that imply we cannot talk to the RPC at
  all (connection refused, DNS failures, TLS / certificate errors).
- `WARNING` — everything else (transient HTTP errors, RPC-level `error`
  responses).
- `WARNING` (not CRITICAL) — RPC timeouts. A timeout under load is expected.

For synchronous code paths (e.g. the learning orchestrator) use
`alert_sync()`. It transparently dispatches to a short-lived worker thread
when an event loop is already running so alerts are **never silently
dropped** from inside an async server.
