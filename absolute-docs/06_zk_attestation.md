# ZK Attestation

ClawGuard uses zero-knowledge proofs in two places: to prove that a content scan was run correctly (ScanAttestation), and to prove that a defense update was legitimately derived from a real caught attack (DefenseUpdateCorrectness). Both circuits use RISC Zero and produce Groth16 seals verified on-chain.

This is the component that makes ClawGuard's network trustless rather than trust-based. Nodes do not need to trust each other's claims. The proof is the trust.

---

## Why ZK Here

Without ZK attestation, the network has a poisoning problem: a malicious node could publish a "defense update" that actually weakens detection — for example, removing a rule that catches a specific attack the malicious node wants to use. Other nodes would pull the update and apply it, believing it came from a legitimate learning cycle.

With ZK attestation, every defense update must come with a proof that:
1. The source attack hash exists in ThreatRegistry (it was a real caught attack, not fabricated)
2. The model weight delta was derived from training on variations of that attack
3. The new rules were derived from the same attack pattern

A malicious node cannot produce this proof for a fabricated update because it cannot construct valid RISC Zero witnesses without having actually run the learning loop on a real attack.

## Circuit 1: ScanAttestation

**Purpose:** Proves that a ClawGuard node ran a content scan according to the published policy, without revealing the content itself.

**When used:** When a node wants to claim a bounty for a published attack hash. The node must prove it actually scanned the content and reached a BLOCK verdict under the current policy — it cannot just copy a hash from someone else and claim the reward.

**Guest inputs (private):**
- `content`: the raw content that was scanned (not revealed)
- `policy_json`: the current detection policy (thresholds, rule version, model version)

**Guest inputs (public):**
- `content_hash`: sha256(content) — must match what was published to ThreatRegistry
- `policy_hash`: sha256(policy_json) — binds the proof to a specific policy version
- `verdict`: the verdict that was reached ("block", "sanitize", "pass")

**What the circuit proves:**
```rust
// Inside RISC Zero guest
fn main() {
    let inputs: ScanInputs = env::read();

    // 1. Verify content hash matches
    let computed_hash = sha256(&inputs.content);
    assert_eq!(computed_hash, inputs.public.content_hash,
        "content hash mismatch");

    // 2. Verify policy hash matches
    let computed_policy_hash = sha256(inputs.policy_json.as_bytes());
    assert_eq!(computed_policy_hash, inputs.public.policy_hash,
        "policy hash mismatch");

    // 3. Run the rule layer inside the zkVM
    let rule_score = run_rules(&inputs.content, &inputs.policy_json.rules);

    // 4. Verify verdict is consistent with rule score and thresholds
    let expected_verdict = if rule_score >= inputs.policy_json.block_threshold {
        "block"
    } else if rule_score >= inputs.policy_json.sanitize_threshold {
        "sanitize"
    } else {
        "pass"
    };
    assert_eq!(expected_verdict, inputs.public.verdict,
        "verdict inconsistent with policy and content");

    // 5. Commit journal
    env::commit(&ScanJournal {
        content_hash: inputs.public.content_hash,
        policy_hash:  inputs.public.policy_hash,
        verdict:      inputs.public.verdict,
    });
}
```

**Journal (public outputs, 96 bytes):**
```
content_hash || policy_hash || verdict_byte
```

**On-chain verifier:** `ScanVerifier.sol` wraps `RiscZeroGroth16Verifier` and checks the journal before approving a bounty claim.

## Circuit 2: DefenseUpdateCorrectness

**Purpose:** Proves that a published defense update (new rules + model weight delta) was legitimately derived from a real caught attack, not fabricated or adversarially crafted to weaken detection.

**When used:** Every defense update published to `DefenseProtocol.sol` must include a valid Groth16 seal from this circuit. `ConsensusVoting` nodes check the seal before casting their vote.

**Guest inputs (private):**
- `attack_content`: the original caught attack content
- `variations`: the adversarial variations generated by the red agent
- `training_data`: the training batch (variations + benign examples)
- `old_weights`: the MLP weights before the update
- `new_weights`: the MLP weights after the update

**Guest inputs (public):**
- `source_attack_hash`: must match an entry in ThreatRegistry
- `rules_hash`: sha256 of the new rules JSON
- `model_delta_hash`: sha256 of the serialized weight delta

**What the circuit proves:**
```rust
fn main() {
    let inputs: DefenseInputs = env::read();

    // 1. Verify the source attack hash is consistent with the content
    let computed_attack_hash = sha256(&inputs.attack_content);
    assert_eq!(computed_attack_hash, inputs.public.source_attack_hash,
        "source attack hash mismatch");

    // 2. Verify variations were derived from the attack content
    // (Each variation must share structural features with the source)
    for variation in &inputs.variations {
        assert!(is_variation_of(&variation, &inputs.attack_content),
            "variation not derived from source attack");
    }

    // 3. Verify the model delta is consistent with training on these variations
    let computed_delta = compute_weight_delta(
        &inputs.old_weights,
        &inputs.training_data,
        LEARNING_RATE,
        EPOCHS
    );
    let computed_delta_hash = sha256(&serialize(&computed_delta));
    assert_eq!(computed_delta_hash, inputs.public.model_delta_hash,
        "model delta hash mismatch");

    // 4. Verify rules were derived from the variation patterns
    let derived_rules = extract_rules(&inputs.variations);
    let computed_rules_hash = sha256(&serialize(&derived_rules));
    assert_eq!(computed_rules_hash, inputs.public.rules_hash,
        "rules hash mismatch");

    // 5. Commit journal
    env::commit(&DefenseJournal {
        source_attack_hash: inputs.public.source_attack_hash,
        rules_hash:         inputs.public.rules_hash,
        model_delta_hash:   inputs.public.model_delta_hash,
    });
}
```

**Journal (public outputs, 96 bytes):**
```
source_attack_hash || rules_hash || model_delta_hash
```

## ZK Toggle

`RISC0_DEV_MODE=1` (default for development and demo): the host emits fake receipts using `RiscZeroMockVerifier`. Sub-second proof generation. The contract surface and API are identical.

`RISC0_DEV_MODE=0`: real Groth16 proofs via `ProverOpts::groth16()`. Proofs take 30–90 seconds on local hardware. Pre-warm before demo with:

```bash
scripts/pre-warm-proofs.sh
```

---

## Proof Cache

Two-tier cache identical to SENTINEL v2:
- L1: in-memory LRU inside the `zk-prover` service
- L2: Postgres `proof_cache` table (migration applied at startup)

Cache key: `sha256(canonical_json(guest_inputs))` scoped by circuit name. Pre-warmed proofs for all three demo scenarios are seeded by `scripts/pre-warm-proofs.sh` before the pitch.
